Inside llama.cpp's quant kernels: profiling decode, and one misaligned byte

July 2026 · CUDA · quantization · Nsight Compute

Why this series

I've spent time in llama.cpp's decode path before — I built a custom Q4_K quantized GEMV kernel and got it within 11% of NVIDIA's production kernel. This series widens the lens: the same profile-first approach, pointed at the rest of the quantization formats and their kernels, looking for the ones leaving performance on the table.

A short glossary, since quant types come up constantly below

llama.cpp runs models in many quantization formats — ways of packing 16-bit weights down to ~2–8 bits so models fit in memory and move faster. The ones that matter here:

  • q4_0 / q4_1 / q5_0 / q8_0 — the classic formats. A block of 32 weights sharing one (or two) scale factors. Simple layouts, and — this becomes relevant — memory-friendly ones.
  • K-quants (q2_K … q6_K) — larger 256-weight blocks with a hierarchy of scales. Better quality per bit, more complex to unpack.
  • I-quants (iq2_xs, iq4_xs, …) — codebook/lookup-table formats. Very tight packing, heavy per-weight decode work.
  • mxfp4 / nvfp4 — the new 4-bit floating-point formats. mxfp4 is what gpt-oss ships in; nvfp4 is NVIDIA's Blackwell format. These are the current frontier formats, which is why I started here.

The question driving this post: for single-token decode, which of these kernels is leaving performance on the table?

Lesson 1: for decode, TFLOPS is the wrong metric

My first benchmark of the quantized matmul kernels reported TFLOPS, and I nearly misread it. Single-token decode is memory-bandwidth-bound, not compute-bound: there's barely any math, you're just streaming the entire weight matrix out of HBM. A 4-bit type only looks "faster" in TFLOPS because the same work is packed into fewer bytes.

The meaningful question is: what fraction of the H200's ~4.8 TB/s does each kernel actually achieve? Rebuilt the table on that basis (shape m=4096, k=14336):

type what it is % of H200 bandwidth
q4_1 classic 4-bit 66.5%
q8_0 classic 8-bit 56.6%
q4_0 classic 4-bit 48.2%
iq4_xs I-quant 4-bit 45.0%
q5_K K-quant 5-bit 44.1%
q4_K K-quant 4-bit 42.5%
nvfp4 frontier FP4 (Blackwell) 39.4%
q6_K K-quant 6-bit 35.2%
mxfp4 frontier FP4 (gpt-oss) 32.7%
q2_K K-quant 2-bit 23.9%

(The very-low-bit I-quants at the bottom of the full table are excluded here: they're genuinely compute-bound from table lookups, so low bandwidth there is expected behavior, not a defect.)

The anomaly: mxfp4 at 33% vs q4_0 at 48%. Both are ~4-bit formats moving roughly the same bytes, so on a bandwidth-bound kernel they should land close together. Instead mxfp4 is ~1.4x slower for the same byte budget. That's not a hardware limit — that's a kernel underperforming. And it's the format a current, real model (gpt-oss) ships in.

Lesson 2: verify what the profiler actually captured

I brought in Nsight Compute to find out why mxfp4 was slow. First attempt: mxfp4 and q4_0 profiled identically — which contradicted the benchmark. The cause: ncu had attached to a small helper kernel (the one that quantizes the input activation vector), which is the same regardless of weight type. I had profiled the wrong kernel, twice.

After targeting the matmul kernel by name, the numbers became meaningful:

metric mxfp4 q4_0
time 21.7 us 16.1 us
DRAM bytes read 31.2 MB 33.0 MB
% of peak BW 29.9% 42.9%
load transactions 19.3M 15.3M

The story is in the contrast: mxfp4 reads fewer bytes yet takes longer and achieves less bandwidth. It isn't starved — it's busy, issuing ~27% more load transactions to move the same data. It's fetching weights in more, smaller, less efficient chunks.

Lesson 3: understand why code is written the way it is before "fixing" it

The source made the cause obvious in one line: mxfp4 loads weights through get_int_b1, which assembles a 32-bit value from four separate byte loads, while the well-performing formats use a single aligned 2- or 4-byte load. Four transactions where one would do — that accounts for the 27%.

It looked like a one-line fix on a frontier format. Then I checked why the byte-load was there, and the block layout answered:

struct block_mxfp4 {
    uint8_t e;       // 1 byte: shared scale
    uint8_t qs[16];  // 16 bytes: the packed weights
};                   // 17 bytes total

The block is 17 bytes, and the weights start at byte offset 1. Every weight sits at an odd address, and aligned loads require aligned addresses. The byte-load isn't an oversight — it's the only correct option for this layout. I tried the aligned load anyway to confirm, and got an immediate Access at 0x...401001 is misaligned. The theory held exactly, which closed the door on the easy fix.

Where this leaves the mxfp4 problem

A real fix means changing the block layout itself — which touches the quantization code, the file format, backward compatibility with every existing model file, and every other backend. That's a design proposal, not a quick patch, and likely a contentious one. I also checked whether the prefill path had found a workaround worth copying: it hasn't, it pays the same byte-load cost. This bottleneck is structural.

What's next

The bandwidth table already points at better-scoped targets — two formats that sit low without being alignment-blocked:

  • nvfp4 (39%) — the other frontier FP4 format, and it already uses aligned loads. Whatever limits it is fixable in the kernel rather than locked into the format. Prime suspect.
  • q6_K (35%) — also uses aligned loads, also underperforming. Second candidate.

Next post: the same profiling process, pointed at those two.

Takeaways

  • Decode is memory-bandwidth-bound: judge these kernels by % of peak bandwidth achieved, not TFLOPS.
  • Verify which kernel the profiler actually captured before trusting the numbers — target it by name.
  • Read why code is written the way it is before changing it: mxfp4's byte-wise loads are forced by its 17-byte block layout, not an oversight.
  • nvfp4 and q6_K underperform without being alignment-blocked — that's where the next post goes.
