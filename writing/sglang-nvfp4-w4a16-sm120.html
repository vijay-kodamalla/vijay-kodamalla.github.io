Marlin vs FlashInfer: benchmarking NVFP4 W4A16 on Blackwell SM120

CUDA · NVFP4 · FlashInfer · CUPTI · August 2026

SGLang issue #33711 asks a narrow question: dense NVFP4 W4A16 layers have no FlashInfer integration on SM120, and FlashInfer exposes one as mm_bf16_fp4. Should SGLang call it? The maintainer attached a condition — this should only be done if it is faster in many cases; if it is not, we should figure out why first.

I had the hardware for it, so I took the issue. This is what the measurement looked like, including two bugs in my own harness that each would have produced a confidently wrong answer.

What runs today

The first thing worth establishing is that "no integration" doesn't mean nothing runs. ModelOptNvFp4A16LinearMethod.apply() calls apply_fp4_marlin_linear() unconditionally — no capability branch, no backend selection. Every dense NVFP4 W4A16 layer on SM120 goes through Marlin today.

That matters because Marlin is an Ampere-generation kernel. Its inner loop issues mma.sync.aligned.m16n8k16 with ldmatrix tile loads — sm80 tensor-core programming. It reads 4-bit weights from HBM, unpacks and scales them to bf16 in registers, then multiplies on 16-bit tensor cores. On Blackwell those instructions still execute through backward compatibility, but they never touch the native FP4 path.

So the real comparison isn't "tuned kernel vs untuned kernel." It's an Ampere-era kernel running in compatibility mode against a Blackwell kernel that FlashInfer's own release notes describe as optimized for SM121, with SM120 needing further work. Neither is a favourite.

One more thing surfaced while setting up the baseline: SGLang's numerical correctness test for this exact path, test_nvfp4_marlin_dense_matches_dequant_reference, was skip-gated to SM80/SM86/SM90. The kernel every SM120 user hits in production had never been asserted correct on SM120 in CI. It passes — rel_l2 0.0033 against a dequantized-weight reference, inside the test's own 0.04 tolerance — and extending that gate to Blackwell became a separate merged PR.

The cuDNN backend never made it into the comparison. mm_bf16_fp4 requires cuDNN ≥ 9.23.1 for that path and the current SGLang release image ships 9.19.0, so the call raises before doing any work. That leaves cute-dsl as the only testable FlashInfer backend.

Two bugs that would have produced the wrong answer

The first result I got was Marlin at 17.6 µs and 2855 GB/s on down_proj at M=1 — a 3.3× win. It's also physically impossible. The card's bus tops out at 1597 GB/s; nothing can read from HBM at 1.79× the bus width.

The cause was in the timing harness. bench_gpu_time_with_cupti takes cold_l2_cache=True by default, but it implements that by scanning input_args for GPU tensors and flushing around them. I was passing a zero-argument closure, so it found nothing, printed a warning I skimmed past, and silently disabled the flush. GB202 has roughly 128 MB of L2 and down_proj's weights are 50 MB — the entire weight matrix stayed resident across iterations. I was benchmarking L2, not HBM.

Passing the tensors explicitly through input_args fixed it. Marlin went from 17.6 µs to 55.4 µs; FlashInfer barely moved, 57.7 to 67.4. The gap collapsed from 3.3× to 1.22×. Marlin had simply been benefiting more from a warm cache, and the headline number I nearly published was wrong by a factor of three.

The second bug was in accuracy. FlashInfer was reporting rel_l2 of 0.0178 against Marlin's 0.0033 — 5.5× worse, flat across every shape and every batch size. A constant error like that is a signature: it's a property of the data, not of the kernel.

My harness was building weights with SGLang's own make_nvfp4_weight_and_ref, which — reading it properly — doesn't quantize anything. It draws the packed FP4 codes from torch.randint and the block scales from an independent torch.randn. Codes and scales are statistically decoupled, and the bf16 reference is built by decoding one against the other. Marlin received exactly those tensors and decoded them exactly. FlashInfer, in my harness, re-quantized the decoded reference — and nvfp4_quantize recomputes each block's scale from the actual data, which for randomly-drawn scales lands somewhere different for most blocks. FlashInfer was being charged for a quantization round-trip Marlin never paid.

The fix was to start from one real bf16 weight, quantize it once, and hand the two kernels the same packed codes in the two scale layouts they each expect — linear for Marlin, 128×4-swizzled for FlashInfer — with an assertion that the packed codes are byte-identical. FlashInfer's error dropped from 0.0178 to 0.0025, and the conclusion inverted: it isn't less accurate than Marlin, it's more accurate.

Both bugs share a shape. Neither crashed, neither produced obviously absurd output, and both would have survived review by anyone not re-deriving the numbers. The only reason the first surfaced was a roofline sanity check — is this number physically possible? — and the only reason the second surfaced was noticing that an error which doesn't vary with anything isn't an error the kernel is producing.

Marlin is faster in 15 of 21 configurations. cute-dsl takes 6, five of which are lm_head at M ≤ 32 — consistent in direction, modest in size at 0.7–3.3%. Marlin's largest margins are on down_proj at low batch, up to 24%.

On accuracy, cute-dsl is better in all 21: rel_l2 around 0.0025 against Marlin's 0.0033, roughly 23% lower, and flat across the batch range.

So the answer to the maintainer's question is no, not as a straight replacement — with a caveat that the split is by shape rather than by batch size, which is not what I predicted when I claimed the issue.

The number that isn't about either kernel

The more interesting result is in the bandwidth columns. On gate_up_proj, both kernels sit around 1015 GB/s — 64% of the card's 1597. On down_proj, 918 GB/s, 58%. On lm_head, 1318 GB/s, 82%.

This is a regime that should be close to saturated. At M=1 on gate_up_proj you read 100 MB of weights to perform about 100 MFLOP of arithmetic — the timing is essentially bytes divided by bandwidth, and nothing else should matter. The flat µs column from M=1 through M=32 confirms it: adding activation rows costs nothing until M=128, when arithmetic finally starts to bite and both kernels drop to ~690 GB/s together.

Yet in the flat region, 36% of the memory bus is going unused, and both implementations leave it on the table in the same proportions. Whatever is capping it isn't specific to either kernel.

I did not chase this to a root cause — that's an Nsight Compute investigation, and it's a different piece of work. But it isn't unique to Blackwell. SGLang issue #22459 profiled the same Marlin W4A16 path for MoE on H20 (SM90) and measured 24% bandwidth utilization against 72% for an FP8 Triton kernel doing twice the byte traffic, attributing the gap to Marlin's dequant pipeline. Two independent measurements, two architectures, same shape of finding.

What I'd do differently

When I claimed the issue I predicted a clear FlashInfer win at small M with a crossover as M grew, reasoning from NVFP4 weights being 4× smaller than bf16. That reasoning was aimed at the wrong axis: both implementations read the same NVFP4 bytes — the byte counts in the harness are identical to the megabyte — so there was never a bandwidth advantage to be had on either side. The comparison was only ever about which kernel converts the same bytes into results more efficiently, and the answer turned out to depend on the shape, not the batch size.

The two harness bugs are the more useful lesson. Both were in the measurement rather than the thing being measured, both produced plausible-looking numbers, and both were caught by asking whether the result was physically possible rather than by re-reading the code. A kernel benchmark is a piece of software, and it deserves the same suspicion as the kernel.
